Where we are

GPTQueue today routes messages to a receiver name supplied by the sender. The MCP server writes to and reads from Redis; a running receiver actively calls receive_message. Redis does not directly stream a task into an agent, and GPTQueue does not yet choose the best agent or launch a durable actor.

The proposed next layer introduces durable actor identities, persisted tasks, explicit runtime presence, actor-scoped wake leases, acknowledgement, and recovery. The offline model exercises those semantics, while the MetaBuilder harness establishes only bounded reference-model evidence—not live-system completion.

What changed in v3
  1. The sender now supplies the current receiver name; intelligent agent selection is shown only as a future option.
  2. The Griller and Respondent sit in a separate intent-clarification conversation, outside delivery infrastructure.
  3. The receiver-to-MCP receive_message call and Redis BLPOP return path are shown explicitly.
  4. A durable actor is separated from its temporary runtime incarnation.
  5. Offline classifications and the inputs used to distinguish them are explicit.
  6. Offline reference conformance is contained in the evidence compartment, not the runtime lifecycle.
Activation input

Conceptual pseudocode for the pure transition model:

TaskQueued(
  actor_id="metabuilder",
  task_id="task-123",
  delivery="wake_if_offline",
  wake_lease_id="wake-456",
)

The production task envelope may eventually contain more fields; the current pure model concentrates on activation and delivery transitions.

Stable actor versus runtime

Actor ID: durable identity used to address work across process restarts.

Runtime ID: one temporary Codex, Pi, or other process currently acting for that actor.

“RuntimeReady” binds a successfully started runtime incarnation to the actor’s wake lease. GPTQueue does not perform that activation today.

Offline classifications

Offline launchable: activation is permitted and the launch contract can run.

Offline store only: activation is intentionally disabled; accepted work waits.

Unavailable: the actor exists, but its launch contract cannot currently run. This blocks the attempt, not necessarily the actor forever.

Griller boundary

The Griller improves the description of the problem through questions. Its result can advise a future selector, but the Griller does not discover recipients, route messages, or participate in ordinary delivery.

Evidence boundary
