Where we are

GPTQueue already provides a live communication path between named agents through MCP and Redis. The system is now moving toward durable task delivery and autonomous receiver activation, so agents can coordinate directly while the surrounding control plane preserves identity, ordering, recovery, and clear limits on authority.

We reached this point by separating current behavior from desired behavior, pinning the exact GPTQueue source, and testing the activation rules as an offline reference model. MetaBuilder has prepared a bounded harness around eleven pure-model cases. That gives us credible evidence for persist-before-wake, wake coalescing, acknowledgement, and recovery semantics, while deliberately leaving live Redis activation, runtime launch, and production policy for a later governed stage.

Four compartments
  1. Communicating agents shows senders, a stable receiver identity, and a direct griller/respondent exchange.
  2. GPTQueue today shows the real MCP, core-store, Redis, BLPOP, and PTY notification path.
  3. Reference model shows the desired persist-before-wake, presence, coalescing, acknowledgement, and recovery semantics.
  4. MetaBuilder harness shows how approved intent and pinned source become bounded, replayable evidence.

Solid versus dotted

Solid arrows are operative flow inside a compartment. Dotted arrows are explanation, advisory influence, future direction, corroboration, or test coverage—not live data flow.

Evidence boundary

The focused 11-case suite establishes only offline reference-model conformance. It does not prove live Redis activation, MCP delivery, runtime launch, end-to-end completion, provider behavior, deployment, or production policy.
